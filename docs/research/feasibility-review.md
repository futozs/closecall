# Feasibility review

An independent agent re-checked claims from the platform and stack reports against primary sources on 2026-11-16. Only claims that were not confirmed are listed.

| Verdict | Report | Claim | Correction |
|---|---|---|---|
| overconfident | apis-macos | SLSIsScreenWatcherPresent() catches any capture in the session (sharing, recording, mirroring/AirPlay); reliability High (empirical) | Only two positive data points exist: Zoom screen share on macOS 26.6.1 (maclens) and `screencapture -V` (headsup). Teams, Meet (Chrome and Safari), Slack, Cmd-Shift-5, Loom, OBS and AirPlay mirroring are all untested in the cited issue. headsup handles mirroring with a separate CGDisplayIsInMirrorSet call, not the watcher. CGSInternal's own header comment says 'Applies to Apple's remote desktop only?'. Present this as 'confirmed for Zoom and screencapture only' until the on-device test matrix in §9 has been run. |
| overconfident | apis-macos | NSWindow.sharingType = .none is reported as ignored by ScreenCaptureKit on 15.4+ | The '15.4+' framing comes only from the original poster. Apple's position is broader: kCGWindowSharingState and NSWindowSharingNone act only at the CGWindow level, so virtually all screen recorders and remote-control apps never honoured them, and there is no public API to prevent capture. The conclusion (hide the app's own UI too) is still right. |
| overconfident | apis-macos | Sequoia Screen Recording re-consent: weekly in beta, monthly at release (TidBITS) | The cited article covers only the change between betas, from weekly to monthly. It does not confirm release behaviour, and Apple has adjusted these prompts since then. The recommendation to avoid Screen Recording still holds, but the cadence should not be stated as fact. |
| overconfident | apis-macos | Homebrew 5.0 deprecated Gatekeeper-failing casks with a disable date of 2026-09-01 | Homebrew announced 'September 2026', not 1 September. The Homebrew 6.0.0 post (June 2026) says the plan was still on track. I did not confirm that enforcement happened. The practical advice (notarize if you want a cask) is unaffected. |
| unverifiable | apis-windows-linux | GNOME 50 removed the X11 session and Mutter's X11 backend | Confirmed as the upstream plan: GNOME 49 disabled the session by default and removal was scheduled for GNOME 50. Fedora 43 had already removed the GNOME X11 packages. The GNOME 50 release notes (18 March 2026) say nothing about X11, and the WebSearch budget was exhausted, so I could not confirm the removal actually shipped. The conclusion that Wayland is the main target holds either way. |
| wrong | stack | Linux lock/unlock trigger: logind session Lock/Unlock signals (plus LockedHint) | Session Lock/Unlock are requests sent to the screen locker, not lock-state notifications, and GNOME does not emit them when it locks itself. Trigger on the LockedHint property change (and on org.gnome.ScreenSaver / org.freedesktop.ScreenSaver ActiveChanged). The apis-windows-linux report gets this right. |
| overconfident | stack | tauri 2.12.5 depends on reqwest only on mobile targets, so a desktop graph can be HTTP-client-free; keep Tauri glue in one crate so a v3 migration stays cheap | The v2 part is correct. But every Tauri 3.0.0 alpha (alpha.0 through alpha.6) depends on reqwest ^0.13 (json, stream) unconditionally: not optional, on all targets. The cargo-deny ban on reqwest/hyper/rustls that the 'provably offline' story relies on would therefore block a v3 upgrade as v3 stands today. Moving to v3 is a policy problem, not just a glue refactor. Track this upstream before committing to that claim. |
| overconfident | stack | zbus skew: atspi 0.30.0 and Tauri notification/single-instance plugins use zbus 5, ashpd 0.14 uses zbus 6; either accept two zbus versions or pin an ashpd built on zbus 5 | atspi→zbus ^5.5, ashpd 0.14→zbus ^6 and single-instance→zbus ^5.9 are correct. But tauri-plugin-notification 2.8.1 depends directly on zbus ^5 and on notify-rust ^4.18 with default features. The current notify-rust 4.19.0 (2026-11-08) pulls zbus ^6 through its default 'z' feature. So the notification plugin alone already brings in both zbus 5 and 6, and pinning ashpd does not fix multiple-versions=deny unless notify-rust is also pinned or its features changed. Plan to allow both zbus versions from the start. |
| unverifiable | stack | Verification limits for this review | The shared WebSearch budget (200 calls per turn) was used up before this step, and the GitHub REST API was unreachable from this machine. Checks therefore used direct WebFetch of primary URLs, the crates.io, npm and Go-proxy APIs, raw.githubusercontent.com, and local SDK/sdef/dlsym probes on this Mac (macOS 27.2, 26B123). Not checked: Opera's AppleScript, Safari private-window enumeration, AX/Apple Events while the screen is locked, the Windows 26H2 capture-border change, the Flatpak PipeWire visibility claims, and the Chromium AT-SPI tab strip. |
