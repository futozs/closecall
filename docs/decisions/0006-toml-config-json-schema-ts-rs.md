# TOML config, generated JSON Schema, ts-rs bindings

## Context and Problem Statement

Rules are the product. People should be able to read, diff and hand-edit them, the settings UI must
use the same types as the engine, and the Rust and TypeScript types must not drift apart.

## Considered Options

- TOML + JSON Schema from `schemars` + TypeScript types from `ts-rs`
- JSON or YAML config
- `tauri-specta` / `specta` for bindings

## Decision Outcome

Chosen option: "TOML, `schemars` schema, `ts-rs` bindings", because TOML is easy to read and diff
and allows comments, `schemars` derives a schema editors can validate against, and `ts-rs` 12 is
stable while `specta` is still a release candidate.

- Types live in `crates/core` (`Config`, `Rule`, `Matcher`, ...). Rust validates; the UI does not
  re-validate.
- `schema/config.schema.json` is generated from `Config::json_schema()` and committed.
- `app/src/bindings/*.ts` is generated by `cargo test -p closecall-core export_bindings` and committed.
- `version` in the config enables migrations; a newer file than the app understands is refused.

### Consequences

- Good, because one source of truth for config, UI and docs.
- Good, because CI can diff generated files and catch drift.
- Bad, because command signatures are not generated: `app/src/ipc.ts` wraps `invoke` by hand,
  following the table in `crates/core/src/ipc.rs`.
- Bad, because the config file itself is sensitive (it may name the user's bank); see [PRIVACY.md](../../PRIVACY.md).

### Confirmation

CI fails when the committed schema or bindings differ from freshly generated ones.
